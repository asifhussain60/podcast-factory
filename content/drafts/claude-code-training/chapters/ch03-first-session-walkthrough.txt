# Getting Up and Running with Claude Code — Your First Session

This chapter is the third and final episode in the series for developers who already use GitHub Copilot in VS Code. Episode one made the case for *why* Claude Code is architecturally different — suggestion-based versus goal-directed, per-keystroke versus per-task. Episode two built the *what* — the agentic loop, the built-in tool kit, CLAUDE.md as persistent project memory, slash commands and Skills, Hooks as the deterministic enforcement layer, MCP for external systems, the permission model and OS-level sandboxing, and the cost model that follows from per-token billing. This chapter is the *how* — the practical walkthrough. By the end of it, a senior developer who has listened to episodes one and two should be able to install Claude Code, authenticate against the right credentials without the per-token-billing trap, navigate into their own project, complete a real change in a real session, generate and refine a CLAUDE.md, and avoid the ten specific friction points that Copilot users consistently hit in their first week. The closing day-one checklist is the action plan — the teacher walking the student out the door with the concrete sequence of moves she can run today.

---

**Part one — prerequisites: what to check before installing**

The honest first move before installing anything is to confirm the machine meets the supported configuration. The official setup documentation at `code.claude.com/docs/en/setup` lists three categories. Operating system: macOS thirteen or later, Windows ten build eighteen-oh-nine or later, Windows Server twenty-nineteen or later, Ubuntu twenty-oh-four or later, Debian ten or later, or Alpine Linux three-nineteen or later. Hardware: four gigabytes of RAM or more, on either an x64 or ARM64 processor. Shell: Bash, Zsh, PowerShell, or CMD — meaning every mainstream developer shell in current use is supported, and the developer does not need to switch shells to use Claude Code.

The prerequisite that traps developers most often is the plan requirement, because it is easy to assume that having a Claude account is enough. It is not. The free Claude dot ai plan does *not* include Claude Code access. What does include it: Claude Pro, Claude Max, Claude for Teams, Claude for Enterprise, or a Claude Console account with pre-paid API credits. If the developer is running a free Claude account, the first authenticated `claude` command will fail with an access error and they will spend ten minutes thinking they have an installation problem when what they actually have is a plan-tier problem. The fix is to upgrade the account to Pro at the lowest tier, or to fund a Console account with pre-paid credits, before running the installer.

Node dot js is the prerequisite that *used* to matter and now does not. The legacy npm install method requires Node dot js. The native installers — covered in part two — have no Node dot js dependency. If the developer's machine has Node dot js for other reasons, it will not interfere. If it does not, that is no longer a blocker. The Copilot-fluent developer reading this can skip the Node dot js setup ritual and go straight to the native installer.

One genuine question from the student lands here, and it is worth answering plainly so it does not hang over the rest of the install. Do I need to uninstall Copilot first, or can they run at the same time? The answer is they run side by side without conflict. Copilot lives inside VS Code as an inline-completion extension and Claude Code lives as a terminal-first CLI with a separate VS Code panel extension. They observe the editor through different surfaces, they consume different credentials, and they do not race for the same hotkeys. Many developers run both — Copilot for the per-keystroke completion rhythm and Claude Code for goal-directed task work — and the two coexist cleanly. There is no uninstall step required to begin.

**Part two — installation: the native installer is the right path**

The strongest piece of guidance for a developer installing today is that the native installer, not npm, is the recommended path. The npm install is the legacy path. It still works, but Anthropic's setup documentation labels it explicitly as legacy and steers new installs to the native installers, which auto-update in the background, install cleanly, and have no Node dot js dependency.

On macOS, Linux, and WSL, the install command is one line in the shell. The developer runs `curl -fsSL https://claude.ai/install.sh | bash` from any prompt. The installer fetches the right binary for the host architecture, places it in a location on the user's PATH, and finishes in a few seconds. On Windows PowerShell, the equivalent line is `irm https://claude.ai/install.ps1 | iex` — the PowerShell idiom for download-and-execute against a script. On Windows CMD, the line is slightly longer because CMD does not have an inline executor: `curl -fsSL https://claude.ai/install.cmd -o install.cmd && install.cmd && del install.cmd` — download, run, clean up.

The package-manager paths are the right choice for developers who prefer to manage everything through Homebrew or WinGet so future upgrades flow through the same tool as the rest of their stack. On macOS with Homebrew, the stable-channel install is `brew install --cask claude-code` and the rolling-channel install is `brew install --cask claude-code@latest`. On Windows with WinGet, the install is `winget install Anthropic.ClaudeCode`. On Linux, Anthropic ships signed apt, dnf, and apk repositories, and the developer can wire those into their package manager the way they would any other third-party signed repo. The trade-off with the package-manager paths is that updates are not automatic — `brew upgrade` and `winget upgrade` are manual steps the developer has to remember to run. The native-installer paths auto-update silently in the background, which is the more hands-off experience.

The VS Code extension is the third install path, and it is worth understanding what it gives the developer beyond what the CLI alone provides. The developer opens VS Code, presses `Cmd+Shift+X` on Mac or `Ctrl+Shift+X` on Windows and Linux, searches "Claude Code," and installs the extension whose publisher is `anthropic.claude-code`. The same extension also installs cleanly in Cursor, Windsurf, and Kiro for developers using those VS Code forks. The critical thing to know — and the thing that surprises a lot of developers in a good way — is that the VS Code extension includes the CLI. Installing the extension is sufficient; the developer does not need to run the native installer separately. For a developer who lives in VS Code and prefers to bring the tool to the editor rather than alt-tab to a terminal, installing the extension is the single move that gets everything.

The legacy npm install is `npm install -g @anthropic-ai/claude-code`. Do not run `sudo npm install -g` — global npm installs with sudo create files owned by root that the developer's normal shell cannot manage cleanly, and they are an ongoing maintenance burden. Use the native installer or the package manager instead. The npm install is documented for the developers whose environments require it, but for everyone else it is the path with the most friction.

Once the install finishes, the verification step is two commands. `claude --version` confirms the binary is on PATH and reports the version that just installed. `claude doctor` runs a detailed health check that covers authentication state, plan tier, model availability, and configuration sanity — this is the right command to run any time a Claude Code session feels off in a way the developer cannot place. One small Windows note: Git for Windows is a recommended optional install because the Bash tool prefers a real Bash environment; without it, Claude Code falls back to PowerShell for shell execution. WSL two is recommended over WSL one for sandboxing support, since sandboxing is built on Linux primitives that WSL two exposes properly and WSL one does not.

**Part three — authentication: the API key gotcha that bills you per token**

The first time the developer runs `claude` in the terminal, the tool opens a browser window for OAuth authorization. The developer signs in with the same Claude dot ai credentials that authorize their Pro, Max, Teams, or Enterprise subscription, and the OAuth flow stores credentials locally. If the browser does not open automatically — common in remote-server environments or some Linux desktop configurations — pressing `c` at the prompt copies the login URL to the clipboard so the developer can open it manually. In WSL two, SSH sessions, or container environments, the OAuth flow may show a code on the device side; the developer pastes that code back into Claude Code at the `Paste code here if prompted` line. To re-authenticate or switch accounts later — for example, when moving from a personal Pro subscription to a work Teams subscription — the developer types `/login` inside a running session, and the flow runs again.

The plans that grant Claude Code access are Claude Pro, Claude Max, Claude for Teams, Claude for Enterprise, a Claude Console account with pre-paid API credits, and Anthropic's deployments through the three major cloud providers — Amazon Bedrock, Google Vertex AI, and Microsoft Foundry. Each of those gives a Claude Code session a way to authenticate; the choice between them is mostly an organizational decision about where the developer's team has already standardized.

Here is where the most expensive new-user mistake lives. Claude Code has a strict authentication-precedence order, and an environment variable from another project can silently put the developer on per-token API billing instead of on their subscription. The precedence, highest to lowest: cloud-provider credentials like `CLAUDE_CODE_USE_BEDROCK`, then the `ANTHROPIC_AUTH_TOKEN` environment variable, then the `ANTHROPIC_API_KEY` environment variable, then any `apiKeyHelper` script the developer has configured, then the `CLAUDE_CODE_OAUTH_TOKEN` environment variable, and at the bottom — only used if everything above is empty — the subscription OAuth credentials that the `/login` flow stored.

The critical gotcha is the fourth-from-top entry: `ANTHROPIC_API_KEY`. Many developers have this variable set in their shell environment for completely legitimate reasons — they have used the Anthropic API directly from a Python or Node script, they have another Anthropic-using tool that wants it, or they exported it months ago for a one-off test and forgot. The moment they run `claude`, that environment variable takes precedence over their subscription. The session works perfectly — the developer notices nothing — and Anthropic bills the developer per token through the API account instead of drawing from their subscription's included usage. A developer can run their first month of Claude Code work on what they think is their flat-rate Pro subscription and then receive an API invoice for hundreds of dollars that they were not expecting.

The student's question lands here exactly as the source anticipated: I have `ANTHROPIC_API_KEY` set in my environment from another project. Does that cause any issues? The answer is yes, it does, and it is one of the first things to fix. The teacher's move is to validate this as real friction — the precedence behavior is not obvious unless the developer reads the auth documentation carefully — and to give the exact two-command fix. First, run `echo $ANTHROPIC_API_KEY` to see whether the variable is set. If it returns a value, run `unset ANTHROPIC_API_KEY` to remove it from the current shell, and remove the corresponding `export` line from the developer's shell profile — `.zshrc`, `.bashrc`, or whichever file is in use — so the variable does not come back next session. After that, the next `claude` run will fall through to the OAuth credentials at the bottom of the precedence list, which is what the developer almost certainly wants.

The credentials, once stored, live in platform-appropriate locations. On macOS, they live in the encrypted macOS Keychain, which is the right secure store for the platform. On Linux, they live in `~/.claude/.credentials.json` with file mode oh-six-hundred, meaning only the owning user can read or write the file. On Windows, they live in `%USERPROFILE%\.claude\.credentials.json` with permissions inherited from the user profile directory. The developer does not normally need to look at these files, but knowing where they are is useful when debugging — for example, if a credential cache has gotten into a bad state and the developer wants to delete it and start the OAuth flow fresh.

For CI/CD and any other non-interactive environment, the right pattern is the one-year OAuth token. The developer runs `claude setup-token` from an interactive session on their workstation, which generates a token good for one year, and then exports it in the CI environment as `CLAUDE_CODE_OAUTH_TOKEN`. From that point, the headless environment authenticates without ever needing a browser. The one-year expiration is the right default — long enough to avoid constant churn, short enough to limit the blast radius of a leaked token.

**Part four — VS Code integration: what the panel gives that the CLI does not**

The VS Code extension requires VS Code one-nine-eight or higher. Older builds will not load it. For a Copilot-fluent developer who has been keeping VS Code current as part of their normal workflow, this is rarely a blocker, but it is worth checking with `code --version` if the developer is on an older corporate-managed VS Code build.

The extension provides a native graphical chat panel that runs alongside the editor — not inline like Copilot's ghost-text completions, but as a panel the developer can dock anywhere in the IDE. The panel is the default surface; the terminal-based CLI inside VS Code remains available and can be switched in settings for developers who prefer it. Changes that Claude Code proposes show as side-by-side diffs before the developer accepts them, which is the familiar review surface for any developer who has merged a pull request — the same green-and-red diff column, surfaced inside the editor at the moment Claude wants permission. Plan mode opens the proposed plan as a full markdown document the developer can edit inline before approving — this is the surface where the developer collaborates with Claude on *what* the work will be before any files get touched. Auto-accept mode is the iterative-work mode where edits flow through without per-edit prompts; the developer reviews the cumulative `git diff` at the end. The at-sign-mention syntax with fuzzy matching lets the developer reference files into the conversation without typing full paths — `@auth.ts` resolves whatever file in the project is the obvious match. Selected text in the editor is automatically visible to Claude — if the developer has highlighted a function and switched to the Claude panel, that function is in context without the developer having to copy it into the prompt.

The extension docks anywhere a VS Code panel can dock: the editor toolbar, the activity bar, the primary sidebar, the secondary sidebar, or as a tab in the editor area itself. A developer who likes the chat to be persistent and unmissable docks it in the activity bar. A developer who wants it tucked away until summoned docks it as a tab. A developer who runs a wide monitor often puts it in the secondary sidebar on the right so the editor stays centered. The flexibility is intentional — different developers have different preferred geometries and the extension does not impose a single layout.

Four keyboard shortcuts cover most daily use. `Cmd+Esc` on Mac or `Ctrl+Esc` on Windows and Linux toggles focus between the editor and the Claude panel — this is the shortcut to learn first because it is the one used most often. `Cmd+Shift+Esc` or `Ctrl+Shift+Esc` opens a new conversation tab, useful when the developer wants to start a fresh thread without losing the current one. `Cmd+Shift+T` or `Ctrl+Shift+T` reopens a closed session — Claude Code preserves session state, so a session closed by accident is recoverable. `Option+K` on Mac or `Alt+K` on Windows and Linux inserts an at-mention reference at the cursor; the same fuzzy matcher that runs from typed at-signs runs from the keyboard shortcut.

Permission modes in VS Code surface as a clickable indicator at the bottom of the prompt box, and clicking it cycles through the four modes: "Ask before edits," "Edit automatically," "Plan mode," and "Auto mode." This is the same set of modes available through the `Shift+Tab` cycle in the CLI, just exposed as a visible indicator with mouse access for developers who prefer the click to the keyboard cycle.

Rewind and checkpoints in VS Code work through a hover affordance. Hovering over any prior message in the conversation reveals the rewind button; clicking it opens the options: fork the conversation from that point, rewind the code only, or rewind both. This is the same checkpoint system that the CLI exposes through `/rewind` and `Esc + Esc`, just surfaced as a hover button — the panel and the CLI share the same underlying state.

**Part five — first session walkthrough: the recommended opening moves**

Once installation and authentication are in place, the session itself starts with two commands. The developer changes into the project directory: `cd /path/to/your/project`. Then runs `claude` from inside that directory. The starting directory matters — Claude Code's write boundary is the directory it was launched from and its subdirectories, so launching from the project root means Claude Code can write anywhere in the project but cannot accidentally reach into the developer's home directory or other projects.

The first screen shows the session welcome — recent session information, the most recent conversations the developer has had with Claude Code on this machine, and the latest updates if anything has changed since the previous session. This is also the moment a Copilot-fluent developer often pauses because the surface is starkly different from Copilot's. The student's question lands here naturally: I opened it and I am looking at a terminal prompt. Where do I start? There are no suggestions appearing.

The honest answer is that Claude Code does not surface suggestions because it does not work that way — Copilot's surface is suggest-something-the-developer-might-type; Claude Code's surface is describe-the-work-and-let-the-agent-execute. The recommended first questions in the official quickstart are the right shape for orienting Claude Code to an unfamiliar codebase. *What does this project do?* — Claude reads the README, the package manifest, and a sampling of source files, and answers in prose. *What technologies does this project use?* — Claude inventories the stack from the manifest and any conspicuous configuration files. *Where is the main entry point?* — Claude finds it by reading the conventional locations for the project's framework. *Explain the folder structure* — Claude walks the directory tree and summarizes what each top-level folder is for. The official documentation puts the supporting fact plainly: "Claude Code reads your project files as needed. You don't have to manually add context." For a Copilot user accustomed to the model seeing only the currently open tabs, this is the right thing to internalize on day one — context comes from Claude reading, not from the developer pasting.

The first code change demonstrates the agentic loop concretely. The developer types `add a hello world function to the main file`. Claude Code does four things in sequence: it finds the appropriate file by reading the project's structure, it shows the proposed change as a diff in the conversation, it asks for approval before writing, and once approved, it makes the edit. The student's question often surfaces right at the approval prompt: it asked me for permission to edit a file. Copilot just edits automatically — is this normal behavior? Yes, this is the default — Claude Code's resting state is read-only with per-edit permission prompts. This is not slowness; this is the safety design from episode two showing up in practice. The developer can change this — moving to `acceptEdits` mode with `Shift+Tab` removes the per-edit prompts and is the right choice for iterative work — but the default is per-edit confirmation for a reason, and the first session is the right time to feel that rhythm before deciding whether to relax it.

**Part six — day-one workflows: what to do in the first real session**

Once the first hello-world change has gone through, the developer is ready to do real work. The two workflows that cover most of what a Copilot-fluent developer encounters in their first week are understanding an unfamiliar codebase and making changes inside one.

The understanding-the-codebase workflow lives almost entirely in Claude Code's strength. The official best-practices documentation frames it: "Use Claude Code for learning and exploration. You can ask Claude the same sorts of questions you would ask another engineer." The prompts that work well are conversational and specific. *Give me an overview of this codebase* — high-level summary. *Explain the main architecture patterns used here* — Claude reads the source and names the patterns it sees. *What are the key data models?* — Claude inventories the type definitions and database schemas. *How is authentication handled?* — Claude traces the auth flow and explains it. *Find the files that handle user authentication* — narrower, returns a file list rather than prose. *Trace the login process from front-end to database* — the across-stack walk that Copilot's per-file completion model has no analog for. A developer ramping onto an unfamiliar codebase — a new hire, a contributor to an open-source project, a contractor onboarding to a client codebase — can compress the first-week exploration substantially by leaning on these prompts before they start writing.

The official guidance on a deeper workflow is the four-step explore-plan-code rhythm, and it is worth running once in the first session to feel it. First, enter plan mode — Claude reads files and answers without making changes. Second, ask for a detailed implementation plan for the change the developer has in mind. Third, press `Ctrl+G` to open the plan in the developer's text editor for direct editing. The plan is a markdown document and the developer can refine it freely — adding constraints, removing steps, rewriting sections to match what they actually want. Fourth, switch out of plan mode and let Claude code against the refined plan. This sequence — explore, plan, then code — is the one that maximizes the chance that what Claude produces matches what the developer actually wanted, and it is especially valuable on any change that touches more than two or three files.

The making-changes workflow is the rhythm most developers settle into for daily work. The prompts are direct, action-oriented, and concrete. *Add input validation to the user registration form.* *There's a bug where users can submit empty forms — fix it.* *Refactor the authentication module to use async slash await instead of callbacks.* Each of these is a complete task, not a step in a larger task, and Claude Code's job is to take the task through to completion — finding the affected files, making the changes, running the tests if test commands are configured, and reporting back. A Copilot-fluent developer often starts by writing prompts that read like Copilot prompts — short, focused on a single function — and gradually scales up as they feel where the agentic loop is genuinely working. That gradual scale-up is the right rhythm; trying to assign a fifty-thousand-line migration on day three is the way to discover sub-agent orchestration before the developer is ready to use it well.

The permission modes are the developer's control dial on how much approval friction sits between the developer and Claude's edits, and learning to move between them is the single biggest workflow improvement available in the first week. The `default` mode auto-approves only reads, which is the maximum-prompt rhythm — the right mode when the developer is exploring or when they have not yet built confidence in what Claude will do with their codebase. The `acceptEdits` mode auto-approves reads, file edits, and common filesystem commands, and is reached by pressing `Shift+Tab` once. This is the right mode for iterative work where the developer wants the rhythm to flow and is comfortable reviewing the cumulative `git diff` at the end. The `plan` mode is reads only and proposes a plan before editing — reached by pressing `Shift+Tab` twice, or by launching Claude Code with `--permission-mode plan`. The `auto` mode auto-approves everything with a background classifier deciding whether each action is safe, and is enabled in settings rather than through the `Shift+Tab` cycle. The `bypassPermissions` mode skips all checks entirely and is meant only for isolated containers and VMs; it requires an explicit flag and should never run on the developer's main machine.

Plan mode is the mode worth understanding in detail because it is the surface where the developer collaborates with Claude on the *shape* of a change before any files get touched. In plan mode, Claude presents its plan and offers the developer five options. *Approve and start in auto mode* — Claude executes the plan with auto-approval on everything. *Approve and accept edits* — Claude executes with edit auto-approval but still prompts for commands. *Approve and review each edit manually* — Claude executes one step at a time with explicit per-edit approval. *Keep planning with feedback* — the developer pushes back on the plan and Claude revises. *Press `Ctrl+G` to edit the plan directly in the text editor* — for the cases where the easiest path is to rewrite the plan in the editor. The five options cover the range from full trust to full review, and the developer picks based on how confident they are in the plan and how much review they want to do.

**Part seven — undoing and recovery: how to back out of a mistake**

The agentic loop occasionally goes somewhere the developer did not intend, and knowing how to back out cleanly is the difference between productive use of Claude Code and learned wariness of it. Four mechanisms cover almost every recovery situation.

`Esc` is the immediate-stop. Pressing `Esc` mid-action stops Claude from continuing whatever tool call it is in the middle of, while preserving the conversation context. The developer has not lost the session — they have just interrupted the current action and can now redirect Claude or correct course before letting it continue. This is the right reach when the developer sees Claude heading somewhere wrong and wants to intervene before the wrong thing happens.

`Esc + Esc` — pressing escape twice in quick succession — or the `/rewind` slash command opens the rewind menu, where the developer can restore the conversation, the code, or both to any earlier checkpoint in the session. From the official documentation: "Claude automatically snapshots files before each change so a checkpoint can restore them." And: "Checkpoints persist across sessions, so you can close your terminal and still rewind later." This is the meaningful safety net — a session the developer thought was lost when they closed the terminal is still rewindable in a future session, because the checkpoints live in the project's metadata rather than in the volatile session.

The "undo that" affordance is conversational rather than menu-driven. The developer types `"Undo that"` and Claude reverts its changes via git — committing the revert or staging it depending on context. This is the right reach when the developer notices a problem after the fact and wants Claude to handle the cleanup rather than digging through git history themselves.

`/clear` resets the context window without ending the session. The developer uses this between unrelated tasks — fixing a bug in module A is over, now starting work on a feature in module B — so the new task starts with a clean slate. The clear preserves what the project loads at every session — CLAUDE.md, the loaded Skills — but drops the conversation history. The student's question fits here exactly: how do I know if the context window is getting full? Does it warn me before performance drops? The `/usage` and `/context` commands surface context usage explicitly — the developer can run them any time to see how much of the context window is consumed. There is no automatic prompt to clear; the developer is responsible for noticing and acting. Building the habit of running `/clear` between unrelated tasks is the cheapest insurance against the late-session degradation that comes from a context window grown too full.

One important warning from the official documentation: "Checkpoints only track changes made by Claude, not external processes. This isn't a replacement for git." The checkpoint system is for the changes Claude makes inside the session. If the developer has a build process or a watcher modifying files in the background, those changes are not captured. Git remains the canonical version control. The right discipline is to make Claude conversational about git itself — the developer can type *what files have I changed?* or *commit my changes with a descriptive message* and Claude will run the git commands, stage what needs staging, and write the commit. Git stays as the safety net under the checkpoint system; the checkpoint system is the lighter-weight in-session affordance for normal recovery.

**Part eight — CLAUDE dot md setup: the day-one move that pays off all week**

Episode two introduced CLAUDE.md as the persistence mechanism for project knowledge. This is the practical section: how the developer actually generates and refines one on day one. The single most useful move is `/init`. Run it inside a project root and Claude Code analyzes the codebase and generates a starter CLAUDE.md automatically. From the official memory documentation: "Run `/init` to generate a starting CLAUDE.md automatically. Claude analyzes your codebase and creates a file with build commands, test instructions, and project conventions it discovers." The result is not the final file — the developer should refine from there — but a generated starting point is much easier to edit than a blank page.

What to include and what to leave out is the question that determines whether CLAUDE.md helps or bloats. The right inclusions are the things Claude cannot guess by reading the code. The bash commands that are specific to this project — the test runner invocation, the lint command, the dev-server command. The code style rules that differ from defaults — when the team uses single quotes and the language ecosystem usually uses double quotes, when the team prefers explicit returns over implicit ones, when the team has a banned pattern. Testing instructions and preferred test runners — which framework to use, how to scope a test run, how to debug a failing test. Branch naming and PR conventions — feature-prefix-slash-description, the title format, the body template. Required environment variables — which ones must be set, which ones have safe defaults, which ones change between dev and prod. Non-obvious project quirks — the data model that looks one way but is actually the other, the function that does extra work despite its name, the file that other files depend on in unintuitive ways.

The right exclusions are equally important. Things Claude can figure out by reading the code — the language, the framework, the obvious architectural patterns. Standard language conventions — there is no need to instruct Claude to use camelCase in JavaScript. Long tutorials or full API documentation — link to the documentation instead, do not paste it. Information that changes frequently — anything that drifts will turn CLAUDE.md into a stale-context source rather than a load-bearing one. Self-evident practices like "write clean code" — these consume context without instructing Claude on anything specific. File-by-file descriptions of the codebase — Claude reads the files directly; the documentation duplicates them and goes stale.

The size recommendation in the official docs is direct: "Target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Two hundred lines is the soft ceiling. Files much longer than that start to lose their effect — the developer is consuming context budget on guidance Claude is less and less likely to actually act on. Better to keep the file tight and link out for the things that genuinely need longer treatment.

The official sample is short enough to internalize whole:

```markdown
# Code style
- Use ES modules (import/export) syntax, not CommonJS (require)
- Destructure imports when possible (eg. import { foo } from 'bar')

# Workflow
- Be sure to typecheck when you're done making a series of code changes
- Prefer running single tests, and not the whole test suite, for performance
```

That is the right scale and the right specificity for a starting CLAUDE.md — concrete rules that name what to do, in language Claude can act on directly. CLAUDE.md can also include other files inline with at-sign references — `See @README.md for project overview and @package.json for available npm commands` — which is the right pattern for pulling in stable reference material without copying it.

The four file locations matter because they correspond to four different audiences. `~/.claude/CLAUDE.md` is the developer's personal rules across all projects — preferences like commit-message style, default review depth, personal banned patterns. `./CLAUDE.md` is the project rules, committed to git, shared with the team — the project conventions that every developer working on this codebase should benefit from. `./CLAUDE.local.md` is the personal project overrides, gitignored, never shared — the developer's own preferences for this one project that the team does not need to know about. The fourth location, mentioned in episode two, is the managed-policy file at `/Library/Application Support/ClaudeCode/CLAUDE.md` on macOS, which is the place enterprise IT writes rules every developer's session must follow.

Auto memory is the second persistence mechanism. Claude Code version two-point-one-five-nine and later writes its own notes to `~/.claude/projects/<project>/memory/MEMORY.md`, and the first two hundred lines or twenty-five kilobytes of that file load into every new session as additional context. The developer manages auto memory through the `/memory` command, which lets them browse and edit both the CLAUDE.md files and the auto-memory file from inside Claude Code. The auto-memory file is plain markdown and is editable and deletable any time the developer wants to curate what Claude has remembered.

**Part nine — the ten Copilot user gotchas: where the friction actually lives**

This section is the highest-value section of the chapter for a developer arriving from Copilot, because these are the ten specific friction points that Copilot users consistently hit in their first week and that nobody warns them about. The teacher's job here is not to dismiss any of them — each is real friction, and a Copilot user who hits one without warning will conclude that Claude Code is broken when in fact the developer's Copilot-trained intuition is just running into a deliberate architectural difference.

*One. No inline completions.* Claude Code has no inline completion. It does not suggest code as the developer types. If the developer expects tab-autocomplete to appear while they type, Claude Code will feel absent — there is no ghost text, no autocomplete suggestion, no hint flowing from cursor. Claude Code's surface is describe-what-you-want and let-the-agent-write-it. A Copilot user who has built the keystroke-rhythm of typing-and-accepting will feel the absence sharply for the first few hours. The right move is to keep Copilot installed alongside Claude Code for the per-keystroke completion rhythm and reach for Claude Code for the goal-directed task work. The two compose; this is not an either-or.

*Two. Human-in-the-loop defaults.* Claude Code defaults to requesting permission before each file change. A Copilot user is accustomed to accepting inline suggestions instantly — no permission dialog, no review surface, the suggestion appears and is gone in a single Tab press. Claude Code's per-edit permission prompts feel slow by comparison, and the developer may initially conclude that this rhythm is unworkable. The fix is to switch to `acceptEdits` mode with `Shift+Tab`. In `acceptEdits`, file edits and common filesystem commands auto-approve and the developer reviews the cumulative `git diff` at the end. This is the right rhythm for iterative work and removes most of the perceived slowness without removing the safety design — `git diff` is still the authoritative review surface for what changed.

*Three. Terminal-first paradigm.* Claude Code is terminal-first. The VS Code extension is a native panel rather than inline, and the strongest experience of the tool is the CLI. A developer who lives entirely inside VS Code's GUI may find the CLI rhythm unfamiliar. The honest framing is that the VS Code panel is a good bridge — many developers do almost all their Claude Code work through the panel — but the CLI is the surface where Claude Code feels most native. Learning to alt-tab to a terminal is worth the effort for the work where the CLI is the cleaner fit, and the panel covers the cases where staying in the editor is the better choice.

*Four. GitHub workflows use standard git and gh CLI, not native Copilot integrations.* Copilot is deeply embedded in GitHub's web UI — PR summaries, reviewer suggestions, and commit messages all happen inside GitHub. Claude Code does the same things through standard git commands and the `gh` CLI. For a developer who already knows git and gh, the translation is direct: "summarize these changes" becomes a prompt, and "create a PR" becomes a `gh pr create` call that Claude Code can make on the developer's behalf. The experience is terminal-first rather than web-native, but the underlying capability is equivalent for most workflows. The shift is from clicking buttons in a web UI to typing prompts that trigger CLI calls; the work that gets done is the same.

*Five. Cost model difference.* Copilot is a flat subscription per seat — the cost does not vary with how hard the developer works on a given day. Claude Code on Pro or Max includes usage within plan limits, and if the developer hits those limits, the session pauses. Claude Code through the Console API is pay-per-token with no soft rate limit. For the developer who does heavy agentic work in a day, the cost question becomes real — not because Claude Code is expensive per se, but because the unit of work is task completion rather than text prediction, and a developer running long agentic loops can consume substantially more tokens than they intuit. The right discipline is to use `/usage` and `/context` to build intuition for the token consumption of the work the developer actually does, and to be deliberate about which work belongs in the agentic loop and which work is better served by a lighter-weight tool.

*Six. Context window management is your job.* Copilot manages context automatically with a small sliding window. With Claude Code, as the context window fills, performance degrades — Claude becomes slower, more likely to forget what was discussed earlier, more likely to make small inconsistency errors. The developer's responsibilities are concrete: use `/clear` between unrelated tasks, use plan mode to scope exploration so the developer is not pulling more into context than necessary, and use sub-agents for large investigations so the high-level conversation does not balloon with the details of the investigation. This is real maintenance work that Copilot users have never had to think about, and naming it plainly is more useful than pretending the tool handles it invisibly.

*Seven. CLAUDE dot md is your Copilot settings equivalent.* Copilot has no persistent project-level memory. Each Copilot session works from what is in the developer's open tabs. CLAUDE.md is how the developer gives Claude persistent context across sessions, and the right way to think about it is as an onboarding document for the AI. Just as a new engineer joining the team would read the project's README and the contributing guide and the architecture document, Claude reads CLAUDE.md at the start of every session. Treating it like an onboarding doc — not like a settings file — is the framing that produces the most useful CLAUDE.md content.

*Eight. Rate limits on subscriptions.* Heavy agentic use on Pro or Max can hit rate limits, at which point the session pauses until limits reset. The Console API has no soft rate limit. For a developer doing intensive agentic work — a long refactor session, a large code-review session, an investigation that runs for hours — hitting rate limits on Pro or Max is a real possibility, and the right response is either to plan around the reset windows, to upgrade to a higher tier, or to move heavy workloads to the Console API where the rate limits are different. The rate-limit pause is not a bug; it is the way Anthropic balances heavy use with subscription pricing.

*Nine. Model is always Claude.* Copilot lets the developer switch to GPT-4o, Gemini, and other models depending on the task. Claude Code only uses Claude models — Sonnet, Haiku, Opus. A developer who has built a workflow around switching models per task will not have that option in Claude Code; the choice is which Claude model, not which provider. This is a deliberate design decision rather than an oversight — Claude Code is tuned for and shipped against Claude models — but it is worth knowing if the developer has a strong preference for a non-Claude model on certain tasks.

*Ten. Run /init immediately.* Copilot needs no per-project setup. With Claude Code, running `/init` at the start of every new project takes a minute and pays back across every subsequent session. It auto-generates CLAUDE.md from the codebase, giving the developer a structured starting point that they refine over the next few sessions. The mental model the teacher wants the developer to land on is that `/init` is the "configure the linter" step for Claude Code — the small one-time setup move that every project should get and that the developer will not regret doing.

**Part ten — key commands reference: what to memorize in week one**

The CLI command set is small enough to learn in one sitting. Running `claude` with no arguments starts interactive mode. `claude "task"` runs a one-time task and prints the result. `claude -p "query"` runs a one-off query and exits — useful for scripts and one-shot questions. `claude -c` continues the most recent conversation, which is what the developer reaches for when they want to pick up where they left off without going through a picker. `claude --resume` opens a picker for previous conversations — the right command when the developer has multiple in-flight sessions and wants to choose which one to resume. `claude --permission-mode plan` starts Claude Code directly in plan mode — useful when the developer knows they want to explore-and-plan before any edits. `claude doctor` runs the health-check covered in part two; reach for it whenever something feels off.

The session command set — the slash commands available inside a running Claude Code session — is what shapes the day-to-day rhythm. `/help` shows all available commands. `/clear` resets the conversation history without ending the session. `/init` generates CLAUDE.md for the project. `/config` opens the settings GUI. `/memory` browses and edits CLAUDE.md and the auto-memory file. `/compact` summarizes the conversation history to free context window. `/plan` switches to plan mode for the current prompt. `/rewind` opens the checkpoint menu. `/permissions` manages the allow and deny rules. `/model` switches the active Claude model. `/usage` shows context window usage and session costs. `/login` re-authenticates or switches accounts. The six commands worth memorizing first are `/init`, `/compact`, `/clear`, `/plan`, `/permissions`, and `/usage` — these six cover most of the day-to-day decisions. The rest are there when the developer reaches for them.

The keyboard shortcuts inside the CLI are short enough to learn passively. `Shift+Tab` cycles the permission mode through default, then `acceptEdits`, then plan. `Esc` stops Claude mid-action while preserving context. `Esc + Esc` opens the rewind menu. `Ctrl+G` opens the current plan in the developer's text editor. `Ctrl+D` or typing `exit` exits Claude Code. The up arrow walks through command history. `Ctrl+R` opens a searchable prompt history — useful when the developer remembers having asked Claude a similar question recently and wants to find the prompt.

**Part eleven — configuration: settings files and custom slash commands**

The settings system uses JSON files at three scopes, mirroring the CLAUDE.md scope design from episode two. The user scope at `~/.claude/settings.json` is private to the developer and applies to every project. The project scope at `.claude/settings.json` is committed to git and shared with the team. The local scope at `.claude/settings.local.json` is gitignored and personal to the developer for this specific project. Settings precedence runs from highest to lowest: managed policy, then command-line flags, then local, then project, then user. This means a project setting overrides a user setting, but a managed-policy setting overrides both — the right ordering for a tool that needs to balance personal preference with team standards with organizational policy.

A starter day-one settings file looks like this:

```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "defaultMode": "acceptEdits",
    "allow": ["Bash(npm run lint)", "Bash(npm test)", "Bash(git status)"],
    "deny": ["Read(./.env)"]
  },
  "autoUpdatesChannel": "stable",
  "editorMode": "vim"
}
```

The `defaultMode` of `acceptEdits` sets the working posture from session start — the developer does not have to remember to `Shift+Tab` into it. The `allow` list pre-approves three specific commands the developer is comfortable with Claude running freely — the lint command, the test command, and `git status` — which removes the permission prompts for the most common safe operations. The `deny` list blocks reads of the `.env` file unconditionally — a sensible default for any project that keeps secrets in `.env`. The `autoUpdatesChannel` of `stable` opts the developer into the stable release channel rather than the rolling one. The `editorMode` of `vim` opts the developer into vim-style keybindings inside the Claude Code CLI for editing prompts.

Configuration also flows through the `/config` command inside Claude Code, which opens a settings GUI for developers who prefer to set values through a menu rather than by editing JSON directly. Both surfaces edit the same underlying files.

Custom slash commands are the extensibility surface that lets a team encode shared workflows as invokable commands. The developer puts a `.md` file in the `.claude/commands/` directory and it becomes a slash command available as `/commandname` in every session. Committing the directory to git shares the commands with the team. The `$ARGUMENTS` placeholder inside the command file picks up whatever the developer types after the command name — `/deploy production` passes "production" into `$ARGUMENTS` and the command file uses it. This is the lightweight extensibility path; the heavier Skills system covered in episode two is the right reach when the workflow needs deeper structure or its own metadata.

**Part twelve — day-one checklist: the action plan the student walks out with**

This is the developer's concrete sequence of moves for their first session — the action plan that lands at the end of this episode. The teacher's role here is to walk the developer out the door with exactly what she needs to succeed.

First, install. Run `curl -fsSL https://claude.ai/install.sh | bash` on macOS or Linux, or install the VS Code extension if the developer prefers the editor surface from the start.

Second, authenticate. Run `claude` and complete the browser-based OAuth login with the Claude dot ai account that holds the developer's Pro, Max, Teams, or Enterprise subscription.

Third, check for the API-key conflict. Run `echo $ANTHROPIC_API_KEY`. If the variable is set from any prior project or test, run `unset ANTHROPIC_API_KEY` to clear it from the current shell and remove the corresponding `export` line from the shell profile so it does not come back. This single step prevents the most expensive new-user mistake — accidentally getting billed per token through an API account when the subscription is supposed to cover the usage.

Fourth, navigate into the project. `cd /path/to/project`. This matters because Claude Code's write boundary is the directory it was launched from and its subdirectories.

Fifth, initialize the project memory. Run `/init`. Review the generated CLAUDE.md, refine it to match the project's actual conventions and quirks, and keep it tight — under two hundred lines is the right scale.

Sixth, explore first. Type *give me an overview of this codebase* and let Claude read the project structure and explain it back. This is both useful in itself and a way to feel the agentic-loop rhythm before asking Claude to do anything destructive.

Seventh, make a small change in plan mode. Press `Shift+Tab` twice to enter plan mode, describe the change the developer wants, review the plan Claude proposes, and refine it before letting Claude touch any files. This is the rhythm to feel for any change that matters.

Eighth, switch to `acceptEdits` for iterative work. Press `Shift+Tab` once to move into `acceptEdits` mode. Let Claude run through iterative changes without per-edit prompts, then run `git diff` at the end to review what changed. This is the right working posture for most day-to-day work.

Ninth, commit CLAUDE dot md to git. Once the developer has refined the generated CLAUDE.md to match the project, commit it. This is what turns the developer's day-one investment into a team-wide benefit — every developer who pulls the project gets the same project-level context, and the next new contributor onboards faster because Claude already knows the conventions.

That is the practical day-one sequence. The chapter closes the way it opened: this is a tool that does real work and requires real effort to use well, and the developer who runs that nine-step sequence in their first afternoon is the developer who will get past the initial friction and into the rhythm where Claude Code earns its place alongside Copilot in the daily workflow. The why was episode one. The what was episode two. The how is what the developer does next — and the day-one sequence above is the cleanest path from understanding to practice.
