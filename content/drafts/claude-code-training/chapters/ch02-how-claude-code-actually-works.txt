# How Claude Code Actually Works — The Agentic Mental Model

This chapter is the second of a three-part series for developers who already use GitHub Copilot in VS Code. Episode one told the audience *that* Claude Code is architecturally different from Copilot — suggestion-based versus goal-directed, per-keystroke versus per-task, assistant versus agent. This chapter explains *why* — the mechanics behind the agentic model. The aim is to leave a senior developer with a working mental model of how the engine functions, so the hands-on session in episode three reads as a sequence of intentional choices rather than as following instructions. Throughout, the comparison anchors against the Copilot experience the audience already knows: Copilot does X at the token level; Claude Code does Y at the tool level. Where Claude Code introduces something Copilot has no equivalent for — persistent project memory, lifecycle hooks, user-spawned sub-agents — that is framed as a new capability to learn, not a gap in Copilot. The chapter does not oversell. When something requires real effort, it says so plainly and explains why the effort is worth it.

---

**The agentic loop — the engine in one sentence**

The cleanest way to describe what Claude Code does is in the words of Anthropic's own documentation: "Claude Code is an agentic coding tool that reads your codebase, edits files, runs commands, and integrates with your development tools." Every verb in that sentence is doing work, and the sentence as a whole is the architectural claim. Claude Code is built around a `while(tool_call)` loop — Claude receives a goal, picks a tool to call, executes the tool, reads the result, decides whether the goal is met or whether another tool call is needed, and then either stops or repeats. The loop runs until the goal is reached, an unrecoverable blocker is hit, or the model decides it needs to ask the developer a clarifying question.

For a Copilot user, the contrast is easiest to feel through a concrete before-and-after. In the Copilot paradigm, the developer types `function getUserById(` and Copilot suggests the function body based on surrounding code. The developer accepts or rejects the suggestion. That is one round-trip — one suggestion, one decision. The cognitive loop is per-keystroke and the loop closes the moment the developer presses Tab or types past the ghost text. In the Claude Code paradigm, the developer types `"The auth tests are failing. Fix them."` Claude Code then runs `npm test -- --grep auth` through the Bash tool, reads the error output, opens the failing test file with the Read tool, reads the implementation being tested, makes a targeted edit using the Edit tool, runs the tests again, reads any remaining failures, iterates, and stops when the tests pass or surfaces a specific blocker to the developer. That entire sequence is one task, not one suggestion. The cognitive loop is per-task, and the developer's role is to review what happened, not to dictate each step.

The structural difference that the loop exposes is this: a language model completing text versus an agent executing a plan across multiple tools and multiple steps. Both are useful patterns. They are not the same pattern. The Copilot loop is fast and pleasant for the parts of the developer's day where they know what they want to write and the AI is filling in the predictable parts. The Claude Code loop is slower per turn but capable of work that no completion-based system can perform, because completion has no notion of running the tests, observing the output, and deciding what to do next. A senior developer coming from Copilot does not have to abandon the per-keystroke rhythm to add the per-task rhythm; the two compose. The point of this chapter is to make the per-task rhythm legible enough that the developer knows when to reach for it.

One natural question lands here, and it deserves a direct answer before going further. If Claude Code reads a file every time it needs to look at it, and every read passes through the context window, does this not scale poorly compared to Copilot's bounded context window? The answer is that it scales differently, not necessarily worse. Each tool call and its result contribute tokens to the context, which is why agentic tasks consume more tokens per task than completion-style assistance does. But the Claude context window is up to one million tokens on current Sonnet and Opus models — roughly an order of magnitude larger than Copilot's 32,000-to-128,000 token range — and a million tokens is enough room to read substantial portions of a codebase across many tool calls without filling up. The cost framing is covered later in the chapter, but the architectural answer is that the loop is designed around the assumption that context is the scarce resource and that tool-call frugality matters. Claude Code reads only what it needs to read, when it needs to read it.

The second question that lands here, and that the chapter will return to, is this: when Claude Code is running tests autonomously, what stops it from running in a loop indefinitely? The short answer is that the loop has natural stopping conditions and several configured ones. Naturally, the loop stops when the goal is met or when Claude decides that further tool calls will not make progress and that the situation requires the developer's input. Configured stops include hard timeouts on individual commands, permission gates that the developer can set at any granularity, and the lifecycle hook system covered in Part 5, which can block specific tool calls before they execute regardless of what Claude wants to do. The agentic loop is bounded — by design, by configuration, and by the developer's choice of permissions.

**The tool system — what the agent has to work with**

The agentic loop is only as expressive as the tools the agent can call. Claude Code ships with a core set of built-in tools that map closely to what a developer does at the command line and in the editor. The list, from the official documentation, is short enough to learn in one sitting and powerful enough that almost every task the developer cares about can be expressed as a sequence of calls against it.

The Bash tool is the universal adapter — it runs any shell command, which means anything the developer can do in a terminal, Claude can do through Bash. The Read tool reads files from the filesystem. The Edit and Write tools make targeted edits to existing files and create new files respectively. The Grep tool searches across files by pattern, the way `grep` or `ripgrep` does in a terminal. The Glob tool lists files matching a pattern, the way `ls **/*.ts` would. The Task tool spawns sub-agents for parallel work, which is the advanced capability covered later in this part. The TodoWrite tool maintains an in-context task checklist that Claude updates as it works through multi-step jobs — a small but disproportionately useful tool for keeping a long agentic session organized. The WebFetch tool fetches content from URLs, for cases where Claude needs to consult documentation or read a referenced page. The ToolSearch tool discovers tools from MCP servers on demand, which is the mechanism that keeps the context window lean even when many MCP servers are connected. That is the core kit. Additional tools come in through MCP, covered in Part 6.

A small example makes the composition visible. Ask Claude "find every Python file that imports `requests` and show me the call sites I should review." Claude reaches for Glob to enumerate the Python files in the project, then Grep to filter that list down to the files containing the import, then Read on each remaining file to look at the call sites in context — three tool calls, no developer keystrokes in between, and the answer arrives as a single response with the relevant snippets quoted. The same question against Copilot would have the developer running the grep themselves and pasting results into chat. The composability of the tool kit is what closes that gap.

A senior developer reading that list will notice that Bash is the universal escape hatch. If a tool does not exist for what Claude needs to do, Claude can almost always reach for Bash and invoke the underlying command directly. This is why the Bash tool is the place where the permission model lives most consequentially — because Bash is what would, if unconstrained, let Claude do anything the developer's shell can do.

The first-week corollary is to write the Bash deny list before the Bash allow list. Add `Bash(rm -rf *)` and `Bash(git push *)` to the deny list on day one through `/permissions`, then expand allows narrowly — `Bash(npm test *)`, `Bash(npm run *)`, `Bash(pytest *)` — for the commands the developer wants Claude running without a prompt. The order matters in two senses: chronologically, because the developer who only writes allows discovers the deny set the day Claude runs a command they wish it had not; and evaluation-order, because the permission system checks denies before allows, so a deny rule cannot be silently overridden by a later broader allow.

There is one architectural fact about write access that should land clearly. From the official security documentation: "Claude Code can only write to the folder where it was started and its subfolders — it cannot modify files in parent directories without explicit permission. While Claude Code can read files outside the working directory... write operations are strictly confined to the project scope." That is a hard boundary, not a default that can be relaxed casually. It means that when the developer runs `claude` from inside `~/projects/my-app`, Claude Code can write anywhere inside `my-app` but cannot reach up into `~/projects` or anywhere else on the filesystem without the developer explicitly authorizing it. This single design choice eliminates an entire category of accidental destruction. A prompt-injected Claude cannot wipe the developer's home directory because Claude Code does not have permission to write there. A first-week pitfall follows directly from this boundary: the directory the developer runs `claude` from *is* the write scope. Launch the binary from `~/projects` to give Claude visibility across several sibling repos and the write scope has just widened to every one of them; `cd` into the specific project first and the boundary stays tight around that single tree. The fix is muscle memory — start every session from the project root, not from a parent.

A second fact about the permission model that surprises new users in a good way is that read-only commands run without prompting. From the official permissions documentation, a fixed set of read-only shell commands — including `ls`, `cat`, `echo`, `pwd`, `head`, `tail`, `grep`, `find`, `wc`, `diff`, `stat`, `du`, `cd`, and read-only git forms like `git status`, `git log`, `git diff` — execute without a permission prompt in every mode. The list is not configurable; it is a built-in safety carve-out for operations that cannot mutate state. This is what makes the agentic loop feel responsive in normal use: Claude is not asking permission every time it wants to look at a file or check the git status, because those operations are categorically safe.

The Task tool deserves its own mention because it is one of the genuinely advanced capabilities Claude Code adds. The Task tool lets Claude spawn parallel sub-agents — what Anthropic's documentation describes as "a lead agent coordinates the work, assigns subtasks, and merges results." This is the mechanism by which Claude Code handles work too large for a single context window, like a 50,000-line migration. The lead agent reads the codebase at a high level, decomposes the work into subtasks that fit individual context windows, hands each subtask to a sub-agent, and merges the sub-agents' results back into a coherent change. For a senior developer coming from Copilot, this is the right capability to know exists but the wrong capability to configure on day one. The first sessions should be single-agent runs against ordinary tasks; sub-agent orchestration is something to grow into when the size of the task makes it necessary. The teacher's job here is to introduce the ceiling, not to make the developer feel they need to reach it before they can use the tool.

**CLAUDE.md and persistent memory — what Claude Code adds: session continuity**

This is the section where a Copilot user is going to ask the most natural question: why do I need this? Copilot just works without per-project setup. The honest answer is that Copilot's much smaller context window means it has never tried to carry project knowledge across sessions — it works from what is in the developer's open tabs in the current editor session. Claude Code has a context window large enough that it can operate across an entire codebase, which means the responsibility of carrying the project's conventions, coding standards, and architectural decisions falls to the developer. CLAUDE.md is how the developer fulfills that responsibility. Frame it as the natural consequence of a more capable context: more power, more responsibility to direct it well. It is real work to maintain, and the chapter does not pretend otherwise.

The session problem, in the words of the official memory documentation: "Each Claude Code session begins with a fresh context window. Two mechanisms carry knowledge across sessions: CLAUDE.md files (instructions you write) and auto memory (notes Claude writes itself)." That sentence is the whole motivation. A new session has no recollection of the last session. Without a persistence mechanism, the developer would re-teach Claude the project's conventions every time they ran `claude`. CLAUDE.md is the persistence mechanism on the human side; auto memory is the persistence mechanism on the model side.

CLAUDE.md is a plain markdown file at the project root — either `./CLAUDE.md` or `./.claude/CLAUDE.md`. Claude Code reads it at the start of every session and loads it into context before the developer's first prompt. From the official docs: "`CLAUDE.md` is a markdown file you add to your project root that Claude Code reads at the start of every session. Use it to set coding standards, architecture decisions, preferred libraries, and review checklists." In practice, a well-written CLAUDE.md does five things: it names the project at the top so Claude has the framing, it lists the coding standards and preferred libraries so Claude does not invent its own, it documents the architectural decisions that are not obvious from reading the code, it gives Claude a review checklist for the kind of work the team commonly does, and it tells Claude what *not* to do — the patterns the team has decided against, the files Claude should not touch, the conventions that look optional but are actually load-bearing.

There are four scopes for CLAUDE.md and they compose rather than override. The managed-policy scope lives at `/Library/Application Support/ClaudeCode/CLAUDE.md` on macOS and is shared across all users in an organization — this is where an enterprise IT or security team writes the rules every developer's Claude Code session must follow. The user scope lives at `~/.claude/CLAUDE.md` and is private to the individual developer; it travels across every project they work on and is the right place for personal preferences like "I write commit messages in imperative mood" or "I prefer functional patterns where reasonable." The project scope lives at `./CLAUDE.md` or `./.claude/CLAUDE.md` inside the project directory; it is committed to the repository and shared with the team, and it is the most important of the four because it is where the project's actual conventions live. The local scope lives at `./CLAUDE.local.md` inside the project directory; it is private to the individual developer for that one project and is added to gitignore, and it is the right place for "I keep my test fixtures in `~/scratch/fixtures` and I want Claude to know about it" without burdening teammates with that detail. All four files are concatenated together when Claude loads context, not overridden — meaning the rules from the managed policy, the user file, the project file, and the local file all show up. Files closer to the working directory take precedence for specificity, which means project beats user when they say contradictory things, but in practice the four files cover different concerns and rarely conflict.

The first-week pitfall here is subtle. A developer writes "always use tabs" in their user CLAUDE.md because they prefer tabs, then joins a project whose project CLAUDE.md says "always use spaces" — and gets confused when Claude switches mid-session. The resolution is the precedence rule above: project beats user, so spaces win, and the developer's tab preference quietly does not apply on this project. Run `/memory` from inside Claude Code to view what is actually loaded across all four files; the visible concatenation is the fastest way to debug a behavior that does not match what the developer expected one file to say.

Auto memory is the second persistence mechanism, and it is the one where Claude carries knowledge forward on its own. Claude Code writes notes to `~/.claude/projects/<project>/memory/MEMORY.md` automatically — saving things like build commands it has discovered, debugging insights from earlier sessions, preferences the developer has stated. The first 200 lines or 25 kilobytes of that file load into every new session as context. The file is plain markdown and is editable and deletable at any time, which means the developer can curate it if Claude has remembered something incorrectly. The split of labor between CLAUDE.md and auto memory is intentional: CLAUDE.md is what the developer wants Claude to know every session, auto memory is what Claude itself has learned across sessions and wants to keep.

One architectural detail matters for a senior developer trying to reason precisely about what CLAUDE.md does and does not do. From the official docs: CLAUDE.md content is "delivered as a user message after the system prompt, not as part of the system prompt itself." It shapes Claude's behavior — strongly, in practice — but it is not a hard enforcement layer. A determined prompt or an unfortunate sequence of events can lead Claude to act against what CLAUDE.md says. For actual enforcement — "block this command no matter what" — the mechanism is Hooks, covered next. The honest framing is that CLAUDE.md is the instruction layer and Hooks are the enforcement layer. Both are necessary; neither replaces the other.

A useful rule of thumb for when to reach for each memory mechanism. If the thing is a fact Claude should hold every session — a coding standard, a preferred library, a directory layout — it belongs in CLAUDE.md. If the thing is a multi-step procedure or an on-demand workflow — "convert this Postman collection to a typed client," "scan the codebase for security smells" — it belongs in a Skill, the custom slash command system covered in the next section. And if the thing must run at a specific lifecycle point — "before any commit, run the linter," "block any `rm -rf` command," "log every tool call to an audit trail" — it belongs in a Hook. The three mechanisms are not redundant; they correspond to three different shapes of need.

**Slash commands — controlling Claude Code from inside the session**

A Copilot user is used to chat as a free-form text input; Claude Code's chat surface is the same, with one important addition. Slash commands give the developer a quick way to invoke specific Claude Code behaviors from inside the chat. From the official commands reference at `code.claude.com/docs/en/commands`: "Commands control Claude Code from inside a session. They provide a quick way to switch models, manage permissions, clear context, run a workflow, and more." Slash commands are recognized only at the start of a message — typing `/` brings up the list of available commands.

The built-in commands worth knowing on day one are a small set. Run `/init` in a new project's root and Claude scans the codebase to generate a starter CLAUDE.md — the right first move when adopting Claude Code in an existing project, because the generated file gives the developer a structured starting point to edit rather than a blank page. Run `/compact` to summarize the current conversation and free context window — pass instructions like `/compact preserve the auth-migration thread` to direct what survives the summary; this is what the developer reaches for when a long session has filled the context and they want to continue without losing the thread. Run `/clear` to start a new conversation while keeping the project memory loaded, which is what the developer wants between unrelated tasks in the same project. Run `/plan` to enter plan-only mode, which is read-only — Claude explores and proposes a plan but does not edit files. Run `/model` to switch the Claude model mid-session, which is useful for matching the model to the work — a heavier model for a hard refactor, a lighter model for a routine cleanup. Run `/permissions` to open the view for managing tool allow and deny rules; this is where the developer goes when they want to pre-approve a category of commands so they stop getting prompted for them. Run `/mcp` to manage MCP server connections. Run `/memory` to edit the CLAUDE.md files and the auto-memory file from inside Claude Code rather than from the editor. Run `/hooks` to inspect the configured hooks for the current session. Run `/context` to visualize context window usage, which is the right command to reach for when the developer wants to understand why a session feels sluggish. Run `/usage` to see session cost and plan limits. Run `/sandbox` to toggle OS-level filesystem and network sandboxing — the deeper safety layer covered later in this chapter. Run `/code-review` to review the current diff at a chosen level and optionally apply fixes. Run `/batch` to decompose a large change into parallel sub-agents — the user-facing entry point to the Task tool's capabilities. Run `/resume` to pick up a previous conversation by name or selection. Run `/rewind` to roll back code and conversation to a checkpoint.

That is more commands than a developer needs on day one. The ones to memorize first are `/init`, `/compact`, `/clear`, `/plan`, `/permissions`, and `/context` — those six cover most of the day-to-day Claude Code experience. The others are there when the developer reaches for them.

There is one design choice in the commands system worth understanding because it matters for how the developer extends Claude Code over time. Custom slash commands have been merged into the Skills system. A `SKILL.md` file in `.claude/skills/<name>/` creates a `/<name>` command available from any session in that project. The key design distinction: CLAUDE.md is always-on context — it loads every session and stays loaded. Skills are on-demand context — they load only when the developer invokes them. This is the right design because it keeps the context window efficient. A team that has ten custom workflows does not want all ten loaded at the start of every session; they want each one available on demand. CLAUDE.md is for the rules that should always shape Claude's behavior; Skills are for the workflows that should be invokable when needed.

**Hooks — the enforcement layer (what Claude Code adds: deterministic control)**

This section introduces something that has no analog in Copilot — not a gap in Copilot, but a capability class that does not exist in the inline-completion model at all. The distinction to land first, before any technical detail: CLAUDE.md is instruction — "please don't do X." A Hook is enforcement — "block any command matching X, regardless of what the prompt says." These are different in kind, not degree. The teacher's way of making it concrete: if you want Claude to never run `git push` on the main branch, CLAUDE.md is a reminder. A Hook is a lock.

From the official hooks documentation at `code.claude.com/docs/en/hooks`: "Hooks are user-defined shell commands, HTTP endpoints, or LLM prompts that execute automatically at specific points in Claude Code's lifecycle. They allow users to inspect events, take action, and optionally return decisions that control behavior." Where CLAUDE.md says "please do X," a Hook says "block unless X." Hooks are the deterministic enforcement layer that CLAUDE.md cannot be.

The lifecycle of a Claude Code session has thirty-five hook events available, and learning them in groups is easier than learning them individually. The once-per-session events are `SessionStart`, `Setup`, and `SessionEnd` — these are where the developer puts logic that should run when a session begins or ends. A common use is `SessionStart` injecting the current git status into context so Claude always knows the working-tree state at the start of every session. The once-per-turn events are `UserPromptSubmit`, `UserPromptExpansion`, `Stop`, and `StopFailure` — these fire around the developer's input. `UserPromptSubmit` is where the developer puts logic that should run before Claude processes the prompt, like substituting placeholders or injecting context. The most important group is the every-tool-call group, which is what makes Hooks the enforcement layer for the agentic loop: `PreToolUse` fires before a tool executes and can *block* the tool call, `PermissionRequest` fires when a permission dialog appears, `PostToolUse` fires after a tool succeeds, and `PostToolBatch` fires after a parallel batch of tool calls. Beyond those, async events like `SubagentStart`, `SubagentStop`, `FileChanged`, `PreCompact`, and `PostCompact` fire on sub-agent lifecycle, file system changes, and context compaction. The thirty-five-event surface is wider than most developers need, but the coverage is what makes Hooks the right layer for any rule that has to run at a specific moment in the loop.

Hooks come in five types, each suited to a different shape of work. A `command` hook runs a shell command, receiving JSON on stdin and responding with JSON on stdout — this is the workhorse type and probably 80% of all hooks a developer writes are of this form. An `http` hook sends an HTTP POST to an endpoint and uses the response to decide what to do — useful when the rule needs to consult a central service. An `mcp_tool` hook calls a tool on an MCP server, which lets Hooks compose with the MCP ecosystem. A `prompt` hook runs a single-turn LLM evaluation, which is the right type when the rule itself requires understanding what is happening rather than pattern-matching it. An `agent` hook spins up a full sub-agent with tool access — the deepest type and the right one when the rule needs to do non-trivial work before deciding.

The decision-control surface for a `PreToolUse` hook is the part of the system that matters most for safety. A `PreToolUse` hook can return `permissionDecision: "allow"`, which skips the prompt and lets the tool call proceed. It can return `permissionDecision: "deny"` with a reason, which blocks the tool call entirely. It can return `permissionDecision: "ask"`, which forces a prompt even if the tool was pre-approved by some other rule. Or it can exit with code 2, which is treated as a blocking error and feeds the error's stderr back to Claude — Claude can then read the error, understand why the hook blocked it, and decide what to do next.

The practical use cases from the official documentation make this concrete. Block any `rm -rf` command before it runs — a one-line shell hook on `PreToolUse` for Bash that reads the tool input from stdin, greps the command field for the destructive pattern, and exits 2 if it matches; Claude then reads the stderr the hook emits and routes around the blocked path on the next loop iteration. Auto-format files after every Edit — a `PostToolUse` hook on file-edit tools that runs the formatter against the changed file. Run lint before every commit — a `PreToolUse` hook on Bash that detects `git commit` and runs the linter, blocking the commit if linting fails. Inject git status into every new session — a `SessionStart` hook that runs `git status` and puts the output into Claude's initial context. Log every tool call to an audit trail for compliance — a `PostToolUse` hook on every tool that appends to an audit log. Auto-approve safe read-only commands to reduce prompt fatigue — a `PreToolUse` hook that pre-approves a list of commands the developer has decided are always safe. Each of these is the kind of rule that has to run at a specific lifecycle point and cannot live anywhere else.

A senior developer reading this will reasonably ask: is configuring Hooks something most developers do, or is this an advanced capability? The honest answer is both. The day-one experience does not require any hooks at all — the default permission system works without them. Most developers acquire their first hook because they hit a specific situation: a command that ran when it should not have, a workflow that needed enforcement rather than reminder, a compliance requirement that needed an audit trail. The first hook is usually one to three lines of shell, configured in `~/.claude/settings.json` for personal scope or `.claude/settings.json` for project scope. A representative first hook is a `PreToolUse` matcher on the `Bash` tool that reads the incoming JSON from stdin, checks the command string for `rm -rf`, and exits with code 2 if it matches — Claude reads the error from stderr, learns the boundary, and routes around it for the rest of the session. As the developer's use of Claude Code matures, they tend to accumulate a small collection of hooks they reach for repeatedly. The capability is configurable from day one but adopted gradually, and that is the right pacing.

Hooks are configured in settings files at three scopes: user (`~/.claude/settings.json`), project (`.claude/settings.json`), and managed policy. The matcher syntax filters by tool name or regex, so the developer can scope a hook narrowly to `Bash` calls matching `git push`, or broadly to all `PreToolUse` events. The configuration is human-editable JSON and the schema is documented in the same hooks reference at `code.claude.com/docs/en/hooks`.

**Model Context Protocol — extending Claude to external systems**

MCP is the part of the Claude Code surface most likely to feel familiar to a Copilot user, because Copilot supports MCP too. The right question to ask is not whether MCP is a Claude Code-exclusive capability — it is not — but what role MCP plays in the agentic loop and how the implementation in Claude Code shapes the developer's experience of using it.

From the official MCP announcement on Anthropic's blog, dated November 25, 2024: "Today, we're open-sourcing the Model Context Protocol (MCP), a new standard for connecting AI assistants to the systems where data lives, including content repositories, business tools, and development environments." The protocol is described as "a universal, open standard for connecting AI systems with data sources, replacing fragmented integrations with a single protocol." That sentence is the design goal in one line. Before MCP, every AI tool that wanted to read from Jira or write to Slack or query a Postgres database had to implement that integration itself, in its own incompatible way. After MCP, an MCP server speaks a standard protocol and any MCP-aware client — Claude Code, Copilot, others — can connect to it.

What MCP solves in practice is the copy-paste problem. From the official docs: "Connect a server when you find yourself copying data into chat from another tool, like an issue tracker or a monitoring dashboard. Once connected, Claude can read and act on that system directly instead of working from what you paste." The pattern is recognizable to anyone who has spent time pasting JIRA tickets or Sentry errors into a Copilot chat to get help with them — MCP eliminates the paste step by letting the tool fetch the data directly.

The concrete examples from the official documentation give a sense of what MCP-enabled workflows look like. "Implement features from issue trackers: 'Add the feature described in JIRA issue ENG-4521 and create a PR on GitHub.'" "Analyze monitoring data: 'Check Sentry and Statsig to check the usage of feature ENG-4521.'" "Query databases: 'Find emails of 10 random users who used feature ENG-4521, based on our PostgreSQL database.'" "Integrate designs: 'Update our standard email template based on the new Figma designs that were posted in Slack.'" In each of these, the value is that Claude is reading and writing against live systems with consistent identifiers rather than against pasted snippets that may be incomplete or stale.

MCP servers can be scoped three ways, which mirrors the CLAUDE.md scopes and serves the same purpose of separating personal from team configuration. Local scope is private to the developer and the current project — the right scope for "I want my personal API token wired into my local Postgres MCP server." Project scope is committed to `.mcp.json` in the project root and shared with the team — the right scope for "everyone working on this project needs the same Jira MCP server connected." User scope is private to the developer across all their projects — the right scope for personal productivity tools the developer wants available everywhere.

The piece of the MCP design that matters most for daily Claude Code use is Tool Search. From the official docs on Tool Search: "Tool search keeps MCP context usage low by deferring tool definitions until Claude needs them. Only tool names and server instructions load at session start, so adding more MCP servers has minimal impact on your context window." The problem Tool Search solves is bloat. Each MCP server contributes tool definitions to the context, and a developer who has connected ten MCP servers — Jira, Slack, GitHub, Sentry, Statsig, Postgres, Figma, Notion, Linear, AWS — could find themselves consuming a meaningful slice of the context budget on tool schemas alone before any actual work begins. Tool Search defers the definitions: at session start only the tool names and server instructions load, and the full schemas load only when Claude needs to call a specific tool.

The numbers Anthropic publishes from their engineering work on Tool Search are striking. The reduction in MCP token usage is 85 percent. Accuracy improves alongside the reduction: "Opus 4 improved from 49% to 74%, and Opus 4.5 improved from 79.5% to 88.1%" on MCP evaluations when Tool Search was enabled. The accuracy improvement is the part that surprises people — the intuition is usually that loading less context should hurt accuracy, not help it. The explanation is that loading every MCP server's tool definitions at session start creates noise: Claude sees fifty tools, gets confused about which to use, and picks suboptimally. Tool Search surfaces the right tools at the moment they are needed and the model picks better when the choice set is focused.

The right framing for a Copilot user is that MCP is a shared open standard rather than a competitive moat. Copilot's adoption of MCP is good news for the ecosystem and for the developer's investment — an MCP server the developer or team builds works against both tools, and the choice between Copilot and Claude Code does not constrain the choice of which external systems to connect. What differentiates the experience of MCP inside Claude Code is the agentic loop around it: an MCP-connected Claude Code session can read a Jira ticket, check the related Sentry errors, query the database for affected users, draft a fix across multiple files, run the tests, and open a PR — all in one continuous session, with the developer reviewing the result at the end. The MCP servers are the same; the loop that composes them is what Claude Code is.

**The permissions model — the safety boundary in detail**

The permissions model is the place where the architectural difference between suggestion-based and goal-directed tools shows up most consequentially. A suggestion-based tool does not need a sophisticated permission system because the developer is reviewing every suggestion before accepting it. A goal-directed tool needs a sophisticated permission system because the developer is reviewing results rather than each step, and the agent is calling tools that can mutate the project and the filesystem.

From the official security documentation: "Claude Code uses strict read-only permissions by default. When additional actions are needed (editing files, running tests, executing commands), Claude Code requests explicit permission. Users control whether to approve actions once or allow them automatically." That sentence describes the resting state. The agentic loop does not get to write to a file or run a command without the developer having said yes — either at the moment, by clicking through a prompt, or in advance, by configuring a rule that pre-approves the tool category.

A second sentence from the same documentation is the critical architectural fact: "Instructions in your prompt or CLAUDE.md shape what Claude tries to do, but they don't change what Claude Code allows. To grant or revoke access, use /permissions, the rules described here, a permission mode, or a PreToolUse hook." Read that sentence carefully because it answers a question that comes up early in every developer's Claude Code adoption. CLAUDE.md cannot grant or revoke permissions. CLAUDE.md says "please" — the permission system says "yes" or "no." This is the cleanest expression of the difference between instruction and enforcement, and it is the reason the four-mechanism stack (CLAUDE.md for context, Skills for workflows, Hooks for enforcement, the permissions system for access) exists rather than being collapsed into one thing.

Permission rules follow a clean syntax: `Tool` or `Tool(specifier)`. Write `Bash(npm run *)` to allow any `npm run` command. Put `Bash(git push *)` in the deny list to block every `git push`. Write `WebFetch(domain:github.com)` to allow fetches only to github.com. Put `Read(./.env)` in the deny list to block reading the `.env` file. Write `mcp__puppeteer__*` to match all tools from the Puppeteer MCP server. The pattern syntax is small enough to learn quickly and expressive enough to cover essentially every rule a team needs. Rules are evaluated in a strict order: deny first, then ask, then allow. The first match wins. Deny always beats allow. This ordering matters because it means a deny rule cannot be accidentally overridden by a broader allow rule — the deny is checked first, and if it matches, no further rules are consulted. The practical consequence for a developer building up a permissions file: write the deny rules first and make them specific to the things that must never happen, then write the allow rules broad enough to be useful, and the ordering does the rest.

Claude Code supports six permission modes that map to different working postures. The `default` mode prompts on first use of each tool, which is the right mode for normal interactive work where the developer is at the keyboard and can answer prompts. The `acceptEdits` mode auto-accepts file edits and safe filesystem commands within the working directory, which is the right mode for tasks the developer wants Claude to handle without check-ins — a long refactor, a documented migration, a test-writing session. The `plan` mode is read-only — Claude can explore but cannot edit source files; this is the mode for "give me a plan before you do anything." The `auto` mode is a research preview that uses model-based classifiers to approve or deny actions; this is the experimental frontier of approval automation. The `dontAsk` mode auto-denies anything that is not pre-approved, which is the right mode for environments where the developer wants to be sure nothing happens that they have not explicitly authorized. The `bypassPermissions` mode skips all prompts entirely — this is meant only for isolated containers and VMs where the safety of the surrounding environment makes the permission system unnecessary; running it on the developer's main machine is dangerous and the documentation flags it as such.

A useful data point from the Anthropic engineering blog on auto mode: "Telemetry showed users approved roughly 93% of permission prompts." Ninety-three percent is the number that motivates the work on auto mode and on sandboxing — when nearly every prompt is rubber-stamped, the prompt itself is contributing more friction than safety, and the right response is to remove the rubber-stamps without removing the safety. That is what auto mode and sandboxing aim to do.

Sandboxing is the defense-in-depth layer beneath the permission system, and it is the place where the architectural difference between asking-permission and being-unable-to-do-harm gets meaningful. From the engineering blog on sandboxing: "In our internal usage, we've found that sandboxing safely reduces permission prompts by 84%." That number is the practical payoff of sandboxing — most prompts the permission system raises are about commands that, in a sandboxed environment, are categorically safe because the sandbox has bounded what they can affect.

Sandboxing is built on operating-system primitives: macOS seatbelt and Linux bubblewrap. Both are kernel-level mechanisms that enforce filesystem and network restrictions on a process and any processes it spawns. From the documentation: "Filesystem isolation ensures that Claude can only access or modify specific directories. This is particularly important in preventing a prompt-injected Claude from modifying sensitive system files." And: "Network isolation ensures that Claude can only connect to approved servers. This prevents a prompt-injected Claude from leaking sensitive information or downloading malware." Both restrictions apply to "any scripts, programs, or subprocesses spawned by the command" — not just to Claude Code itself. This is what makes sandboxing the defense-in-depth layer: a malicious command that escapes Claude's awareness still cannot reach files or network destinations the sandbox has not authorized.

The combination of the permission system and sandboxing produces the right shape of safety for an agentic tool. The permission system asks before doing anything that could mutate state outside a small read-only safe set. Sandboxing makes the consequences of an unsafe action bounded even if the permission system is bypassed or misled. Neither layer alone is sufficient for serious autonomous work; together they are.

**The cost and context model — predicting what a session will spend**

The last piece of the mental model for a senior developer coming from a flat-monthly-subscription tool is the cost model. Copilot charges a fixed monthly rate per seat for unlimited completions; the cost of a Copilot session does not vary with how hard the developer works that day. Claude Code is token-billed for API usage, which means every agentic loop iteration — every tool call and its result — passes through the context window and contributes to the bill. A single "fix the auth tests" request might involve ten to twenty tool calls, each contributing tokens to the context. A long refactor might involve hundreds.

The critical framing for a Copilot user is that the comparison is not tokens-for-tokens. Copilot's flat subscription buys unlimited completions because completion is the bounded unit — each completion is bounded by the cursor and by the model's response length. Claude Code's agentic loops are unbounded by the same measure but accomplish work that would otherwise require many round-trips of human-driven completion cycles. The right comparison is task completion versus text prediction. A single agentic task that takes Claude an hour and consumes some non-trivial token budget might be substituting for a developer-day of focused work; the math is rarely close in favor of the developer-day even when the token bill looks large in isolation.

The context window is the resource the developer should pay most attention to, because the cost model is downstream of how the context fills. Claude Code sessions use Claude's full context window — up to one million tokens on current Sonnet and Opus models. For comparison, GitHub Copilot's context window is 32,000 to 128,000 tokens depending on model. The order-of-magnitude gap is what makes the agentic loop possible at scale — a million tokens is enough room to read through a mid-sized codebase, hold the conversation history, retain CLAUDE.md and any loaded Skills, and still have headroom for tool calls and results.

Context compaction is the mechanism that keeps long sessions from hitting the wall. When the context window fills, the `/compact` command — or automatic compaction triggered by the system — summarizes the conversation, preserving CLAUDE.md, the loaded Skills, and the key facts the conversation has established. After compaction, CLAUDE.md is re-read from disk and re-injected to make sure the rules are still loaded. Compaction itself is a Claude API call that costs tokens — there is no free way to summarize — but the cost of compaction is much less than the cost of continuing to grow the context until performance degrades. From the official docs: "Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills." A senior developer planning a long session should think about when to compact the same way they think about when to checkpoint a long-running script.

The practical advice for a Copilot user adopting Claude Code on cost: start with default mode for a few sessions to get a feel for how often Claude asks permissions and how many tool calls a typical task involves. Run `/usage` to watch session cost against plan limits, and run `/context` to visualize what is filling the window — together they build intuition for the token consumption of different kinds of work. Move to `acceptEdits` mode for the tasks where the per-step permission prompts are not contributing real safety. Configure a small set of pre-approved tool patterns for the commands the developer is comfortable with Claude running freely. Reach for Skills when the workflow recurs, because Skills load on demand rather than always-on. Reach for Hooks when the rule must be enforced rather than reminded. Enable sandboxing whenever the work allows it. Each of these choices reduces friction or cost or risk in a way that makes the agentic loop more practical for daily work.

The cost is real and the chapter does not pretend otherwise. A developer using Claude Code heavily for substantive agentic tasks consumes meaningfully more tokens than a developer using Copilot to autocomplete the same number of lines. The justification is not that the token bill is smaller — sometimes it is, sometimes it is not — but that the unit of work is different. A token budget spent on an autonomous task that completes a migration in hours is a different transaction from a token budget spent on completions that fill in keystrokes the developer was going to type anyway. The senior developer making the call on whether Claude Code is worth its cost is reasoning about which kinds of work belong in the agentic loop and how much of the team's effort can be redirected from doing-the-work to reviewing-the-result. That is the framing the chapter wants to leave the listener with — not "cheap versus expensive" but "what shape of work is the spend buying."

**Where this leaves the listener — and what episode three covers**

By the end of this chapter, a senior developer coming from Copilot should have a clear working model of how Claude Code operates. The agentic loop is `while(tool_call)` — receive a goal, choose a tool, execute, observe the result, decide whether to call another tool or stop. The tools are a small kit of built-ins centered on Bash, Read, Edit, and the search-and-list utilities, extensible through MCP servers that speak a shared open protocol. Persistent project knowledge lives in CLAUDE.md, which loads at the start of every session and shapes Claude's behavior without binding it. On-demand workflows live in Skills, which load when invoked and keep the context lean. Lifecycle enforcement lives in Hooks, which can deterministically block or modify tool calls at thirty-five distinct points in the session. External system access lives in MCP servers, which the developer connects once and uses across sessions. Safety lives in the permission system and in sandboxing — the former asks before risky actions, the latter bounds the consequences if anything slips through. Cost is metered per token and the agentic loop consumes more tokens per task than completion does, justified by the kind of work the loop is doing.

That mental model is what episode three runs on. Episode three is the hands-on session — prerequisites, installation, authentication, the VS Code extension, the first real session against the developer's own codebase, common workflows like fixing failing tests and writing a CLAUDE.md from scratch, the gotchas that come up in the first week, and a reference card for the daily commands. The arc of the three episodes is why, what, and how — episode one was the why, this chapter has been the what, and episode three is the how. The listener should arrive at episode three knowing what Claude Code is and what each piece of it is for, so the install-and-run experience reads as putting the pieces into practice rather than as following steps blindly.

The chapter closes the way it opened: this is a tool that does real work and requires real effort to use well. CLAUDE.md is maintenance. Hooks are configuration. The permission model is a discipline. The cost model is an ongoing decision. None of these are gaps — they are the shape of a tool built for goal-directed work rather than for inline completion. The developer who internalizes the mental model in this chapter is the developer who will use Claude Code well, deliberately, and for the work it is actually designed for. That is the only way this tool earns its place in a workflow that already has Copilot in it, and the rest of the series is about making the path from understanding to practice short enough that the developer can walk it in an afternoon.
